# Grammar Error Detection & Correction — Classical NLP

A grammar checker built entirely with **classical NLP** techniques (no deep
learning / transformers): statistical n-gram language modeling, POS-tagging
based rule systems, and edit-distance spell checking. Designed in two
strictly separated layers so the NLP engine can be tested and tuned for
accuracy on its own, independent of the OS integration.


## Why classical NLP (no deep learning)?

| Component | Classical technique used |
|---|---|
| Fluency / candidate ranking | Trigram language model, add-k smoothing, trained on Brown corpus |
| POS tagging | NLTK's averaged perceptron tagger (statistical, not neural) |
| Spelling correction | Norvig edit-distance (1–2 edits) + corpus word frequencies |
| Grammar rules | Deterministic POS-pattern rules + curated collocation lists |

This mirrors how early production grammar checkers (e.g. early Grammarly,
LanguageTool's rule engine) actually worked before neural GEC models.

## Rule coverage (30 categories)

| Category | Example fix |
|---|---|
| Subject-verb agreement | "He go" → "He goes" (incl. do-support negation, coordinated verbs, compound-predicate/PP-aware subject finding) |
| Do-support / modal verb form | "don't knows" → "doesn't know", "can sings" → "can sing", "should to study" → "should study" |
| Progressive construction | "am go" → "am going" (BE + bare verb → BE + -ing) |
| Perfect tense participle | "have saw" → "have seen" |
| Present perfect duration | "is working since 2020" → "has been working since 2020" |
| Existential there agreement | "There is many people" → "There are many people" |
| Each/every agreement | "Each students" → "Each student" (cascades to fix the verb too) |
| Article usage (a/an) | "a elephant" → "an elephant"; re-checked after other edits |
| Demonstrative agreement | "this books" → "these books" |
| Tense consistency | "went ... and buy" → "went ... and bought" |
| Confused words | their/there/they're, its/it's, then/than, your/you're, to/too/two... |
| Directional their/there | "go their" → "go there" |
| Double negatives | "don't have no money" → "don't have any money" |
| Preposition errors | "married with" → "married to", "senior than" → "senior to", "prefer X than Y" → "to Y", "discussed about" → "discussed" (inflection-aware) |
| Duration preposition | "since two hours" / "from five years" → "for ..." |
| Dative movement | "explained me the problem" → "explained the problem to me" |
| Indirect question order | "asked me where was I going" → "where I was going" |
| Conditional mood | "If I will get time" → "If I get time" |
| Countable/uncountable | "many water" → "much water" |
| Pluralized uncountables | "informations" → "information" |
| Pronoun case | "Me and him went" / "between you and I" → corrected |
| Reflexive pronouns | misused reflexives corrected |
| Pronoun-antecedent agreement | "the company ... their" → "its" (singular institutional nouns) |
| Comparative/superlative | "more better" → "better" |
| Redundant phrases | "free gift" → "gift" |
| Adverb placement | "I always am happy" → "I am always happy" |
| Passive voice | detection-only style advisory (off by default) |
| Missing-apostrophe contractions | "dont" → "don't" |
| Punctuation & capitalization | sentence-initial cap, "i"→"I", missing terminal punctuation, "!!!"→"!", day/month/language/nationality capitalization |
| Sentence fragments | detection-only |
| Comma splices | detection-only (correctly ignores subordinate "if/when/because..." clauses) |
| Spelling | Norvig edit-distance + corpus frequencies (expanded with modern/British vocabulary + curated overrides for known-wrong-ranking cases) |

**Advanced patterns added for harder ESL/conditional/word-order errors**
(12 more modules, covering the hardest tier of the external test sets):
predicate nominative articles ("I am student"→"a student"), demonstrative
subject-verb agreement ("These is"→"are"), numeral-noun agreement ("two
brother"→"brothers"), subordinate-clause tense consistency ("when I
arrive"→"arrived"), quantifier-of-phrase agreement ("each of the students
have"→"has", "a number of X is"→"are"), gerund-after-preposition ("look
forward to meet"→"to meeting"), modal-perfect ("would helped"→"would have
helped"), had-inversion ("Had I knew"→"Had I known"), negative-adverb
inversion ("Hardly I had"→"Hardly had I"), by-the-time past perfect,
not-only-but-also parallelism, and subjunctive mood after insist/suggest/
recommend.

## Setup

```bash
pip install -r requirements.txt
python build_models.py     # one-time: trains the n-gram LM + builds spell-check frequency table
```

This downloads NLTK's `punkt`, `averaged_perceptron_tagger`, `brown`, `words`,
and `wordnet` corpora automatically on first run.

## Step 1 — Test the engine (Layer 1) standalone

```bash
# Interactive:
python test_cli.py

# One-off:
python test_cli.py "He go to school everyday and eat a apple."

# Run the full accuracy evaluation:
python tests/evaluate.py
```

**Current benchmark (153 hand-labeled sentences, 40+ error categories):**
- Overall exact-match accuracy: **99.3%**
- False-positive rate on already-correct sentences: **0%** (60 clean sentences)
- Precision: **100%** · Recall: **98.9%** · F0.5: **99.8%**

To improve accuracy further: add more labeled sentences to
`tests/test_cases.py` covering error types you care about, run
`python tests/evaluate.py`, and tune the relevant rule in `engine/rules/`.
**Do this entirely within Layer 1** — no need to touch `desktop_app/` at all.

## Step 2 — Use it system-wide (Layer 2, once you're happy with Layer 1's accuracy)

```bash
python desktop_app/hotkey_listener.py
```

Then, in **any application** (Word, Gmail, Google Docs, Notepad, Slack...):
1. Select some text
2. Press **Ctrl+Alt+G**
3. The selection is replaced with the corrected version

Platform notes:
- **Windows**: works out of the box.
- **macOS**: grant Accessibility + Input Monitoring permissions to your
  terminal/Python under System Settings → Privacy & Security.
- **Linux**: works under X11 out of the box; Wayland restricts global
  hotkeys by design (bind the script at the compositor level instead).

Layer 2 contains **zero grammar logic** — it only calls
`engine.corrector.GrammarCorrector.correct()`. This means you can re-tune
rules, retrain the LM, or add new error categories in Layer 1 and Layer 2
keeps working unchanged.

## Known limitations (honest, since this is classical NLP)

- **POS-tagger ambiguity**: words that are both common nouns and verbs
  (e.g. "plays", "raining" as NN vs VBG) can be mistagged without deeper
  semantic context — a known weakness of statistical POS taggers vs.
  contextual neural models. This is the one category of error the
  benchmark still misses.
- **Small-corpus contraction/collocation bias**: the Brown corpus is
  formal/journalistic text, so pure LM-based scoring can misjudge rare
  (but valid) word combinations. We compensate with deterministic
  POS-pattern guards for the highest-risk cases (their/your/its followed
  by a noun or adjective, "than" after a comparative, etc.) — this took
  real iteration to get right; see the comments in `confusion_words.py`.
- **Curated lists, not first principles**: preposition collocations,
  redundant phrases, and singular-collective nouns (company/government/
  etc. vs. team/band, which are deliberately excluded — see
  `pronoun_antecedent.py`) are curated lists of common cases, not derived
  from general rules. This is also how rule-based checkers like
  LanguageTool handle these categories in practice.
- **Fragments/comma-splices are detection-only**: we flag them but don't
  auto-rewrite, since the correct fix depends on the writer's intent.
- **Passive voice is a style advisory, off by default**: passive voice
  isn't a grammar error, so `GrammarCorrector.correct()` doesn't surface
  it unless you pass `include_style_advisories=True`.
- **Compound/complex sentence structure**: rules handle simple coordination
  ("X and Y") reliably, including nested cases (subject-finding skips past
  prepositional-phrase objects and earlier coordinated verbs); deeply
  nested subordinate/relative clauses can still confuse the heuristics.
- **POS-tagger context bias**: right after "do"/a modal/"have", the tagger
  often labels an obviously-conjugated word ("knows", "sings", "saw") as
  base-form (VB) simply because base form is *expected* there — which
  defeats a naive tag-based check. `modal_verb_form.py` and
  `perfect_tense_participle.py` check the word's surface form directly
  (via lookup tables) rather than trusting the tag in this specific
  position, for exactly this reason.
- **Word-order rules are pattern-matched, not parsed**: indirect-question
  order and conditional mood are detected via specific trigger patterns
  (reporting verb + wh-word + AUX + subject; "if" + comma + "will"), not a
  real parse tree. They're conservative by design (narrow trigger
  conditions) to avoid false positives, but won't catch variations outside
  those patterns.
- **Genuinely hard, not attempted**: word-order errors beyond the specific
  patterns above, general pronoun-antecedent number agreement for people
  (singular "they" is standard, correct English and is deliberately left
  alone), and anything requiring semantic coreference resolution or a
  real dependency parse.
- **Deliberately skipped despite being tractable-looking**: two patterns
  from the harder external test set were left unfixed on purpose rather
  than force a fragile answer:
  - **Dangling modifiers** ("Having completed the assignment, the laptop
    was switched off.") — detecting this requires knowing a laptop can't
    complete an assignment, i.e. real-world/semantic knowledge, not syntax.
  - **Double-object verb restructuring for "suggest"-type verbs**
    ("He suggested me to take a break.") — unlike "explain"/"describe"
    (handled by `dative_movement.py`), the natural fix here has several
    equally valid rewrites ("suggested that I take a break", "suggested I
    take a break", "suggested taking a break"), so hardcoding one specific
    rewrite would be matching one test's answer key, not a real fix.

## Extending

1. Add a new rule module in `engine/rules/your_rule.py` with a `check(tagged_sentence, tokens)` function
   returning a list of `{start, end, type, message, suggestion}` dicts. Use `suggestion: None` for
   detection-only rules (no auto-fix), `"__DELETE__"` to remove a token, or `"__INSERT_AFTER__<text>"`
   to insert text after a token — `engine/corrector.py` understands all three.
2. Add it to the `correction_rule_outputs` list (or the detection-only block) in `engine/corrector.py`.
3. Add labeled test cases to `tests/test_cases.py` for the new error type — include both an error
   case AND a "clean" case that could plausibly trigger a false positive. Also test interaction with
   existing rules (deletions/substitutions can invalidate downstream agreement — see the article
   re-check pass in `corrector.py` for an example of handling this).
4. Run `python tests/evaluate.py` and confirm accuracy holds (especially the false-positive rate)
   before touching `desktop_app/`.
